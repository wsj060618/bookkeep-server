# AGENTS.md

Multi-module Spring Boot 3.5.16 / JDK 17 / Maven backend for a bookkeeping web app. Four modules: `bookkeep-common` (Result/exceptions/JWT), `bookkeep-model` (entities + DTOs), `bookkeep-service` (mappers/services), `bookkeep-web` (controllers/config). `PLAN.md` (in Chinese) is the authoritative design doc — read it before writing code. This file only captures what is not obvious from the repo.

- **Category templates are per-account, books only get a copy** (PLAN §5.4.1/§10.4): `category_template` + `category_template_item` (both **physical delete**, no `deleted` column) hold the user's own templates; the built-in 「班级班费」 is **not a row** — it is `id = 0` and its content is `CategoryPresets.classCategories()`, so it can never drift from the 13 categories seeded at registration. `book.category_template_id` records which template the current categories came from (`NULL` = built-in). **`POST /api/books` takes `{name, templateId?}` (`BookCreateReq`) and seeds that template's categories** — the primary way to choose a template, because switching later requires an empty book. `CategoryTemplateService.itemsOf(id)` is the shared resolver (`null`/`0` → built-in). `POST /api/category-templates/{id}/apply` **refuses (400) when the book already has transactions** — replacing categories would break the category ownership of existing transactions, so it never migrates them silently. Applying is a **copy** (logic-delete old categories + insert template items), so deleting a template does not touch books that already used it (`BookMapper.clearTemplateRef` only nulls the pointer, including books in the recycle bin). There is deliberately **no template-item editor**: to change a template, fix the categories in a book and hit 「存为模板」. `constant/CategoryTemplate` was renamed to **`constant/CategoryPresets`** when the `CategoryTemplate` entity appeared — do not reintroduce the old name.
- **Books are now multi-book** (PLAN §2.1/§5.2): create seeds the categories of the **chosen template** (default: built-in 13) in a transaction and auto-switches current; delete is soft-delete into a 15-day recycle bin; **the last book cannot be deleted** (400) because every other endpoint resolves `current_book_id`. Recycle-bin read/restore/physical-delete **must stay handwritten SQL** in `BookMapper` — MyBatis-Plus logic delete appends `deleted=0` to generated SQL, so Wrappers can never see or restore a deleted row. `book.deleted_at` exists for the retention window (`deleteById` does not write it).
- **Scope was deliberately shrunk (PLAN §2.4)** — do not "helpfully" re-add these: personal/merchant book types, budget, AI analysis, avatar upload (OSS), multi-user shared books. Multi-book management **was** cut and later came back (list/create/rename/switch/delete + recycle bin — see the bullet above and PLAN §5.2); book *types* are still single (`class`). There is exactly **one** book type: `book.type = 'class'`, `CategoryPresets.classCategories()` is the built-in preset (13 categories: 8 expense + 5 income), and `RegisterReq` has **no** `bookType` (`bookName` is optional, defaults to 班级账本). `book.share_token` + `book.share_token_expires_at`: the public-page link is **not** created at registration — it is generated by `POST /api/books/{id}/share` and lives **3 days**; sharing again replaces the token and kills the old link (single-link model, see PLAN §5.9). `BookResp.shareToken` is therefore nullable, and `BookResp.shareTokenExpiresAt` must travel with it.
- **Deployment target (PLAN §1)**: local-first on Windows (Nginx for Windows serves the built frontend and reverse-proxies `/api` to `127.0.0.1:8080`; backend binds loopback only), plus an optional Docker Compose target on a rented server **only during a free trial / interview week** — no long-term server. The user rejects ongoing server cost; do not propose paid hosting as a requirement.
- **Security baseline (audit 2026-11-07, full report in `docs/security.md`)**: `support/AuthThrottle` (Caffeine) limits login/registration — prod: 5 failures per `IP+email` / 5 min, 30 login requests per IP / min, 5 registrations per IP / hour; dev defaults are deliberately loose, strict values live in `application-prod.yml`. `config/ProdSecurityGuard` **refuses to start under `prod`** when `jwt.secret` is the repo default or shorter than 32 chars. `LogAspect` never falls back to printing raw arguments. Cloud artifacts are tracked in `docker/` (`Dockerfile`, `docker-compose.yml`, TLS `nginx.conf`, `.env.example`, runbook); `deploy/` remains machine-local and gitignored. Do not publish 3306/8080 in compose — the app sets `SERVER_ADDRESS=0.0.0.0` only inside the compose network.
- **Single-machine deploy lives in `deploy/`** (W3, `deploy/README.md` is the runbook) — the whole directory is **gitignored** (scripts + machine config + build artifacts, `git rm -r --cached deploy` was applied), so it is machine-local and never committed: keep machine-specific values in `env.ps1` (DB creds, `JWT_SECRET`, MySQL/frontend paths, `HTTP_PORT`); `APP_BASE_URL` left blank there and `start-all.ps1` derives it on every start from the current LAN IP + `HTTP_PORT` (write it only for a fixed domain/HTTPS), with `env.ps1.example` as the template. Everything needed to run lives inside it: `app/bookkeep.jar` + `web/` (frontend dist copy) + `nginx/runtime/` + `logs/` + `run/` + `backup/`, so the folder can be copied to another machine as-is. `deploy/build.bat` (`build.ps1`) runs `mvn -pl bookkeep-web -am -DskipTests package` from the repo root, copies `bookkeep-web/target/bookkeep.jar` → `deploy/app/bookkeep.jar`, and copies `env.ps1`'s `FRONTEND_SRC` → `deploy/web/` (it refuses to run while 8080 is listening, since Windows locks the jar). `start-all.bat` / `stop-all.bat` / `backup.bat` / `restore.bat` / `build.bat` are **ASCII-only launchers**, the logic is in the same-named `.ps1` — cmd mis-parses UTF-8 Chinese batch files (PLAN §8 第 32 条), so never move the logic or Chinese messages back into `.bat`. `nginx/nginx.conf` is a template whose `__FRONTEND_DIST__` is replaced into `nginx/nginx.generated.conf` on each start (single source of the frontend path, i.e. `env.ps1`'s `FRONTEND_DIST = Join-Path $PSScriptRoot 'web'`); the `root` value must stay **quoted** in the template or nginx rejects any path containing spaces. All script paths derive from the script's own location, so the folder can be moved/copied to any path — only `env.ps1` holds machine-absolute paths (`MYSQL_HOME`, `FRONTEND_SRC`, optional `BACKEND_ROOT` for `build.bat`). The jar is started with cwd = `deploy/` so logs land in `deploy/logs/`.
- **Password reset is email-only (PLAN §10.2)**: `POST /api/auth/forgot-password` `{email}` (always returns the same HTTP 200 message — anti-enumeration) and `POST /api/auth/reset-password` `{token, newPassword}`. Tokens are 32 random bytes stored as **sha256** in `password_reset_token`, 15-minute TTL, single use; a new request invalidates the user's other unused tokens. Mail uses QQ SMTP (`spring-boot-starter-mail`, `smtp.qq.com:465`, authorization code), configured by `MAIL_USERNAME` / `MAIL_PASSWORD` / `MAIL_FROM` (pure address) / `MAIL_FROM_NAME` (display name) + `APP_BASE_URL`; when unconfigured the endpoint still returns 200 and only logs a warning. The old `--reset-password` CLI and the `WebApplicationType.NONE` branch are **removed** — do not reintroduce an unauthenticated password-write path. **Any code path that writes `user.password` must bump `token_version`** (change-password and email reset both do).
- `application.yml` now sets `server.address: 127.0.0.1` (only Nginx may face the LAN) and reads `jwt.secret` from `${JWT_SECRET:...}` — changing that value invalidates every issued token.
- **Login is by email; username is only a display name**: `LoginReq` is `{email, password}`, and the failure message is `邮箱或密码错误` (never reveal whether the email exists). Email format has **one** definition: `bookkeep-model`'s `validation/EmailRules.PATTERN` (`@Pattern`, mirrored by the frontend's `src/utils/validate.ts`) — plain Jakarta `@Email` is deliberately **not** used, it accepts `123@qq`, `a@b.c` and even `张三@qq.com`. `user.email` is `NOT NULL` and unique among live rows (`uk_user_email_active`, case-insensitive) — that is why `forgot-password` only needs the email. `nickname` is **gone** (column dropped; `UserResp` has no such field); the UI displays `username`, which `PUT /api/users/me` may change. **Changing the email requires the current password**; changing only the username does not. `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`, `/api/books` (8 endpoints: `GET` list, `POST` create, `PUT /{id}` rename, `POST /{id}/share` → 3-day public link, `PUT /{id}/current` switch, `DELETE /{id}` → recycle bin, `GET /trash`, `PUT /{id}/restore`), `/api/categories` (4 endpoints), `/api/category-templates` (5 endpoints: `GET` list, `POST` snapshot, `PUT /{id}` rename, `DELETE /{id}`, `POST /{id}/apply`), `/api/transactions` (6 endpoints incl. `/balance` and `/export`), `/api/statistics/{summary,category}`, `GET /api/public/report/{shareToken}`, `/api/users/me` (3 endpoints: `PUT` profile, `PUT /password`, `DELETE` account) and `POST /api/auth/{forgot-password,reset-password}` exist. Login returns `{token, user, books}` (**flat**, `books` is a sibling of `user`, not nested inside it — PLAN §5.1 records this; each book carries `shareToken` + `shareTokenExpiresAt`, possibly both null when the user never clicked 分享). `/me` returns only `UserResp` — books must come from `/api/books` or the login response. Treat `PLAN.md` as the spec — do not assume code referenced there already exists.
- `SecurityConfig` is the **day-7 final** version plus the public report path and the two password-reset endpoints: it permits only `/api/auth/register`, `/api/auth/login`, `/api/auth/forgot-password`, `/api/auth/reset-password`, `/api/public/report/**`, `/error`; `anyRequest().authenticated()`; stateless; `JwtAuthenticationFilter` runs before `UsernamePasswordAuthenticationFilter` and only **authenticates** (invalid token → no authentication, chain continues), so the single 401 JSON writer is `JwtAuthenticationEntryPoint` and the single 403 writer is `JwtAccessDeniedHandler` (both real status codes + the standard `{code,message,data}` envelope). Do **not** turn `JwtAuthenticationFilter` into a `@Component` — Boot auto-registers every `Filter` bean in the servlet container, so it would run twice; `SecurityConfig` instantiates it manually. The filter does exactly one DB read per authenticated request (`userMapper.selectById`) to compare `user.token_version` with the token's `ver` claim — that is how a password change/reset kills old tokens; do not add more queries there. A soft-deleted user still passes the filter (`selectById` returns null → authenticate), so the business layer keeps doing the `401` for that case. Do **not** permit `/api/auth/**` wholesale (`/me` must stay authenticated), and do **not** widen the public matcher beyond `/api/public/report/**` (that path is the only anonymous data出口).
- Exception policy (final, PLAN §5): **business errors are HTTP 200 + `body.code`** regardless of code (400/401/403 alike, e.g. `/me` for a soft-deleted user → 200 + `code=401`); **only authentication/authorization failures use real 401/403**, written by the two handlers above. `GlobalExceptionHandler` must keep its explicit `@ExceptionHandler(AccessDeniedException.class)` — without it the catch-all `Exception` handler swallows `@PreAuthorize` denials into 200 + `code=500`. Frontend therefore checks `code` in the success branch and `error.response.status` in the error branch.
- SQL lives in `sql/`: `schema.sql` (full schema, for fresh installs) and one-off `ALTER` migrations for already-built DBs (`migration_add_user_avatar.sql`, `migration_username_reusable.sql`, `migration_book_type_class.sql`, `migration_book_deleted_at.sql`, `migration_user_token_version.sql`, `migration_share_token_expiry.sql`, `migration_email_required.sql`, `migration_email_login.sql`). The class-book migration also flips historic `book.type` rows to `class` and adds `book.share_token`; `migration_book_deleted_at.sql` adds the recycle-bin timestamp — **run both on any existing DB before starting the app**, otherwise book/trash queries fail with `Unknown column 'deleted_at'`. Historic `deleted=1` books get `deleted_at = NULL`, which the purge deliberately ignores. `migration_user_token_version.sql` adds `user.token_version`; **skip it and every user query fails with `Unknown column 'token_version'`** (MyBatis-Plus always selects the full column list). `migration_share_token_expiry.sql` adds `book.share_token_expires_at` and back-fills existing links with `now + 3 days`; skip it and every book query fails with `Unknown column 'share_token_expires_at'`. `migration_category_template.sql` adds `book.category_template_id` + the two template tables (`category_template`, `category_template_item`); **skip it and every book/category-template query fails with `Unknown column 'category_template_id'`**.
- Commits are incremental (Chinese `feat:`/`docs:` messages). A root `.gitignore` covers `target/`, `logs/`, `.idea/`, `.env`, `application-local.yml` — still be deliberate about what you stage. `http/` holds replayable IDEA HTTP Client scripts (one per finished module, PLAN §6.1); `http/auth.http` is the P1 acceptance script. `docs/接口文档.md` is the frontend-facing API doc (Tlias-style: 基本信息/请求参数/响应数据 per endpoint) — it is a third mirror of the contract next to `PLAN.md` §5 and the frontend's `src/types/api.ts`, so changing a DTO means updating all three.

## Modules

- Dependency direction is one-way: `bookkeep-web → bookkeep-service → bookkeep-model`, and `bookkeep-service → bookkeep-common`. `bookkeep-model` and `bookkeep-common` are leaves that must **not** depend on each other, on service, or on web (model = data shapes only, common = envelope + utilities).
- Parent pom (packaging=pom) holds `dependencyManagement`; submodules declare dependencies **without versions**. Do **not** add a `<dependencies>` block to the parent (the reference project VirtueEdu does that and ends up polluting every leaf module with `spring-boot-starter-web`).
- All modules share package root `com.bookkeep`, but the app class lives in `com.bookkeep.web` — default component scan would only cover `com.bookkeep.web`, so `BookkeepApplication` **must** keep `scanBasePackages = "com.bookkeep"` or `@Component`/`@Service` beans in `common`/`service` will not be found. Keep `@MapperScan("com.bookkeep.service.mapper")` as well.
- `bookkeep-model` depends only on `mybatis-plus-annotation` + `jakarta.validation-api` + lombok: entities carry `@TableName/@TableId/@TableLogic`, DTOs carry `@NotBlank/@Size/@Email`. Changing a table's columns means editing an entity here, not in `service`.
- `application.yml` and `logback-spring.xml` live **only** in `bookkeep-web`, which is the only runnable module (it owns `spring-boot-maven-plugin` + `build-info`).

## Build / run

- No Maven wrapper — use system `mvn`.
- Build: `mvn clean package` (root) → runnable `bookkeep-web/target/bookkeep.jar` (`<finalName>` is `bookkeep`). Dev run: `mvn spring-boot:run` from `bookkeep-web`; production: `deploy\build.bat` (jar + frontend collected into `deploy\`) then `deploy\start-all.bat` (see `deploy/README.md`).
  - `spring-boot:run` in a single module resolves `com.bookkeep:{common,model,service}:1.0.0` from the **local repository**, so on a fresh machine run `mvn -pl bookkeep-web -am install -Dmaven.test.skip=true` once first (otherwise `Could not resolve dependencies`). In IDEA, just run `BookkeepApplication` with `DB_USER`/`DB_PWD` in the run configuration's environment variables.
- Requires local MySQL (8.4 in this environment) database `bookkeep` (utf8mb4). Credentials are **not** hardcoded: `application.yml` uses `${DB_USER}` / `${DB_PWD}` and fails fast if unset.
  - PowerShell session: `$env:DB_USER="root"; $env:DB_PWD="..."` **in the same window** before `mvn spring-boot:run` / `mvn test`.
- JDBC URL must use `characterEncoding=UTF-8`, **not** `utf8mb4` (Connector/J takes a Java charset name; `utf8mb4` throws `UnsupportedEncodingException`).
- To (re)build the DB manually: `& "D:\Program Files\MySQL\MySQL Server 8.4\bin\mysql.exe" -uroot -p -e "source D:/coding/bookkeep-server/sql/schema.sql"`. PowerShell does **not** support `<` redirection — use `source`, not `mysql < file`.
- To wipe and rebuild from scratch (dev only, **loses all data**): drop the database first, then run `schema.sql` — that file is self-contained (`CREATE DATABASE IF NOT EXISTS` + `USE` + all 5 tables), so no other script is needed:
  ```powershell
  $mysql = "D:\Program Files\MySQL\MySQL Server 8.4\bin\mysql.exe"
  & $mysql -uroot -p -e "DROP DATABASE IF EXISTS bookkeep;"
  & $mysql -uroot -p -e "source D:/coding/bookkeep-server/sql/schema.sql"
  ```
- Logs roll into `logs/` (daily, 30-day retention, ERROR split to `-error.log`); SQL logging on below `prod` profile.

## Conventions to follow when implementing (from PLAN.md)

- API prefix `/api`, envelope `{code, message, data}` (`Result`/`ResultCode`/`PageResult`/`BusinessException` belong in `common`), `code=200` success, 401 JSON on bad token.
- Data isolation: front-end never sends `book_id`; backend derives it from `user.current_book_id` and reads the user via `SecurityUtil.getUserId()` (not by re-parsing the token). Every query must enforce book ownership.
- `SecurityUtil.getUserId()` lives in `bookkeep-common` (only needs `spring-security-core`) and reads the `Long` principal that `JwtAuthenticationFilter` puts into the `SecurityContext`; anonymous requests have a `String` principal, so it throws `BusinessException(UNAUTHORIZED)`. It deliberately does **not** call `JwtUtil` — token parsing happens once, in the filter. Services call it directly; controllers must not accept a `userId` parameter from the client.
- Login never distinguishes "user not found" from "wrong password" — both throw `BusinessException(BAD_REQUEST, "用户名或密码错误")`, otherwise the endpoint becomes a username oracle. `AuthLoginTest.unknownUserMessageIsIdentical` guards this. Soft-deleted users fall into the same branch for free (MP's logic-delete filter hides them from `selectOne`).
- Service layer is interface + `impl` (e.g. `AuthService`/`AuthServiceImpl`, interface in `com.bookkeep.service`, impl in `com.bookkeep.service.impl`). Entities/DTOs live in `bookkeep-model` (`com.bookkeep.model.entity`, `com.bookkeep.model.dto.req|resp`); mappers live in `bookkeep-service`.
- `bookkeep-service` has no `spring-security` dependency of its own — `PasswordEncoder` reaches it transitively via `bookkeep-common`'s `spring-security-core`, and the only bean is declared in `bookkeep-web`'s `SecurityConfig`. Inject the interface, not `BCryptPasswordEncoder`.
- Batch inserts: **do not** use MyBatis-Plus's static `Db.saveBatch(...)` inside a transactional service. It fetches its own `SqlSession`, and with an outer `@Transactional` + MySQL `REPEATABLE READ` the rows can land outside the caller's transaction snapshot — the symptom is brutal: the SQL log shows 13 inserts, yet a query in the same transaction returns 0 rows (this broke every P2 API test). `AuthServiceImpl` now inserts the 13 template categories one by one via `categoryMapper.insert(...)`: same session, same transaction, and 13 rows make batching pointless. If real bulk import is ever needed, use `IService.saveBatch` on a Spring-managed service (or the mapper's `insert` in a loop inside the transaction), never the static `Db` helper.
- `AuthServiceImpl.register` deliberately pre-checks the username **and** catches `DuplicateKeyException`. The pre-check only gives a friendly message; real uniqueness comes from the **generated-column** index `uk_user_username_active` (`IF(deleted=0, username, NULL)`), so a **soft-deleted user no longer holds the name** — re-registering a 注销过的 username is legitimate and guarded by `AuthRegisterTest.softDeletedUsernameCanBeReused`. `DuplicateKeyException` is now only for two *concurrent* live registrations of the same name.
- `user.username` is `utf8mb4_0900_as_cs`: usernames are **case-sensitive**, `Tom` and `tom` are two accounts. Do not "helpfully" lowercase usernames in code. Consequence: any query by username must add `deleted=0` (MP does it automatically; handwritten SQL must), otherwise a live row and its tombstone both match. Usernames are now **display names only**, so they may contain Chinese (even spaces/punctuation): `UsernameRules` (model `validation/`) is the single rule — **length only, ≤20 chars** (`MAX`/`MESSAGE`, enforced by `@Size`), mirrored by `USERNAME_MAX` in `RegisterView`/`SettingsView`. There is deliberately **no** charset `@Pattern`; do not reintroduce one.
- **Only *new* passwords are validated**: `PasswordRules` (model `validation/`, 6–32 位, 字母/数字/下划线**至少含两种** — pure digits/letters/underscores are rejected; mirrored by `PASSWORD_PATTERN`/`passwordRule` in the frontend's `utils/validate.ts`) applies to `RegisterReq.password`, `PasswordUpdateReq.newPassword` and `ResetPasswordReq.newPassword` — **never** to `oldPassword`, login, or delete-account, because historic passwords may contain symbols and must keep working.
- Collation is deliberately two-layered: database/tables/every other column are `utf8mb4_0900_ai_ci` (MySQL 8 default), only `user.username` / `user.username_active` are `utf8mb4_0900_as_cs`. Comparing **two columns** with different collations raises `Illegal mix of collations`; comparing a column with a string parameter is fine. Never compare `username` to another table's text column.
- 封禁 must **not** reuse `deleted` — the generated column only looks at `deleted`, so marking a ban there frees the name for impersonation. Bans need a separate `status` column with `deleted=0`.
- Money is `BigDecimal` with `DECIMAL(12,2)` columns — never `double`. Every money value leaving the API is a two-decimal **string** (global `BigDecimal → String` serializer), so `0` from `COALESCE(SUM(...))` must be scaled to `0.00` (see `StatisticCalculator.money`) or the frontend gets `"0"` in one place and `"0.00"` in another.
- **Statistics口径 has exactly one implementation**: `StatisticCalculator` (`service/support`). Logged-in `/api/statistics/*` and the anonymous `/api/public/report/*` must both go through it (public page derives `bookId` from `share_token` **and requires `share_token_expires_at > now()`**, never from `SecurityUtil`). `month` is parsed there too: blank → current month in `Asia/Shanghai`, malformed → `BusinessException(BAD_REQUEST)`; never silently return empty data.
- **Running balance (`balanceAfter`) is a MySQL window function inside a CTE, filtered in the outer query.** The CTE covers the whole book; the month/date filter goes *outside*. Filtering inside makes every month restart at 0. `OVER (ORDER BY trans_date, id)` — the `id` is mandatory (same-day rows otherwise flip order and the balance jumps).
- Export is CSV built as `byte[]` in `bookkeep-service` (`export/TransactionExportService`) — no `HttpServletResponse`/`MultipartFile` in the service layer; the controller only sets headers (`text/csv`, `ContentDisposition.attachment().filename(name, UTF_8)`). Hard requirements: **UTF-8 BOM**, two decimals, `yyyy-MM-dd`, and CSV quoting for `,` `"` newline in notes. Success is a file, but parameter errors still return the normal `200 + {code:400}` JSON envelope, so clients must branch on response type.
- Logic delete is configured globally but **only applies to MyBatis-Plus generated SQL** — handwritten `@Select`/statistics SQL must add `deleted=0` itself.
- `budget` is **out of scope** (PLAN §2.4): the table stays in `schema.sql` but there is no `Budget` entity, mapper or API. Do not build it. (If it is ever revived: the table has no `deleted` column, so no `@TableLogic`; budgets are hard-deleted so `(book_id, category_id, month)` doesn't collide on re-create.)
- `transaction` is a keyword-ish table name — backtick it in handwritten SQL.
- Category names are unique per `(book_id, type)` **at the application layer only** (`CategoryServiceImpl.requireNameAvailable`, create + rename). There is no DB unique index behind it, so it is a friendly-error check, not a race-safe constraint. `type` must stay in the key: the 13-category template deliberately has two 「其他」 (one expense, one income).
- Dates pass as `yyyy-MM-dd`; statistics match via `DATE_FORMAT(trans_date,'%Y-%m')=#{month}`. Jackson is GMT+8.
- Business code logs via Lombok `@Slf4j`; controller calls are auto-logged and password/token-masked by `LogAspect` — don't duplicate logging in controllers. `LogAspect` JSON-serializes args, so `MultipartFile` upload args must be skipped/placeholder-ed.
- Log levels: `LogAspect` records **every** controller exception at **ERROR** — business ones (`BusinessException`, e.g. wrong password, duplicate username) without a stack trace, unexpected ones with the full stack. `GlobalExceptionHandler` additionally logs business errors at WARN. Consequence: `logs/*-error.log` is **not** "only real bugs" — two failed logins produce two ERROR lines by design. Don't add ERROR-level alerting on that file without filtering `业务异常`.
- jjwt is 0.12.x: `signWith(SecretKey)` requires `Keys.hmacShaKeyFor(...)`, not a raw string.
- Avatars are **out of scope** (PLAN §2.4): `user.avatar` stays as a reserved column, but there is no upload endpoint and no `FileService`. If revived: store only a URL string, keep `MultipartFile` out of the service layer, and put OSS credentials in env vars.
- Comments: **only explain "why", one line when possible**. No line-by-line narration and no long javadoc blocks — the project owner explicitly asked for this after P2 (`TransactionServiceImpl` was trimmed from 62 to 14 comment lines). Non-obvious reasoning that needs more than a line belongs in `PLAN.md` §8 (pitfalls) or the commit message, not in the code.
- Known gaps are tracked in **PLAN §9** (no global rate limiting — which is a **precondition for any public deployment**; email is required but **unverified** (no confirmation mail); forgot-password only has an in-process limiter; register is not idempotent; no long-term hosting). They are deliberate — do not silently "fix" them mid-phase.

## Testing

- Tests live in each module's own `src/test/java`; `@SpringBootTest` + MockMvc integration tests go in `bookkeep-web` (full context, needs MySQL + env vars). Test classes must end in `Test` (Surefire default). `spring-security-test` is deliberately **not** a dependency: tests use real tokens (its `@WithMockUser` principal is a `User`, not the `Long` that `SecurityUtil` expects).
- `DataSourceConnectionTest` is the current smoke test (connection validity, `SELECT 1`, table count); it reads `application.yml`, so `DB_USER`/`DB_PWD` must be set or it fails with an unresolved-placeholder error.
- `GlobalExceptionHandlerTest` deliberately defines its own throw-away endpoints in a nested `@TestConfiguration` + `@RestController` (never in `src/main`, or they would ship as public endpoints). It asserts HTTP 200 + `body.code`/`message` (only the `accessDenied` case is a real 403), and runs with `@AutoConfigureMockMvc(addFilters = false)`: it only tests exception mapping, and those throw-away endpoints have no token, so the security chain would turn every case into 401.
- `SecurityJsonHandlerTest` is a plain JUnit test (no Spring context) calling `JwtAuthenticationEntryPoint` / `JwtAccessDeniedHandler` directly: P1 has no roles, so a filter-chain 403 is not reachable from an integration test, and this pins the "real 401/403 + identical envelope" contract the frontend depends on.
- `AuthMeTest` tests the real chain end to end (register → login → `Authorization: Bearer <token>` → `/api/auth/me`) and does **not** use `@WithMockUser`: that principal is a `User` object, while `SecurityUtil` only accepts a `Long` (the token subject), so `@WithMockUser` would prove nothing about the filter. Use real tokens in any future authenticated integration test.
- Tests that write data (e.g. `UserMapperTest`) put `@Transactional` on the test class, so Spring rolls back after each method — the rows are **never persisted**, so do not go looking for test data in MySQL. `-DskipTests` also skips nothing but compilation, so "green build" alone means tests were not run; use `mvn -pl bookkeep-web -am test` with env vars set.
- `BookMapperTest` / `CategoryMapperTest` insert rows under fake ids (`TEST_USER_ID = 999_999`, `TEST_BOOK_ID = 999_999`) instead of `1`: the rollback protects the DB, but a *query* filtered by `user_id = 1` would also match real rows created by manual testing and fail confusingly.
- `StatisticApiTest` / `ExportApiTest` / `PublicReportApiTest` are the W2 ones: they create data through the real HTTP API (so the balance check and category template apply), assert **two-decimal strings** (`"0.00"`, never `0`), and hand-check the arithmetic. `ExportApiTest` decodes the response as UTF-8 and asserts the BOM (`\uFEFF`), the running-balance column, and CSV quoting; it never writes a file to disk. `PublicReportApiTest` sends requests **without** `Authorization` on purpose — that is the contract — and uses `AuthHelper.shareToken(...)` (login, then `POST /api/books/{id}/share`) to mint a fresh 3-day link.
